# MAC 기반 패턴 판별기 (Cross / X)

## 1. 실행 방법
```bash
python main.py
```
### ⑴ 실행 환경
- Python 3.8 이상, 표준 라이브러리(json, time, os)만 사용합니다.
- `data.json`은 **main.py와 같은 폴더**에 두어야 합니다.
- 실행 후 모드를 선택합니다.
  - `1` : 사용자 입력 모드 (3×3 필터 A·B, 패턴을 직접 입력)
  - `2` : data.json 분석 모드 (5×5, 13×13, 25×25 일괄 판정)
  - `0` : 종료

<br>

1 1 1           0 1 0           1 1 1

## 2. 구현 요약

### ⑴ 데이터 구조
- n×n 패턴/필터는 2차원 리스트로 저장합니다.
- `create_matrix`, `set_value`, `get_value`로 생성·저장·조회합니다.

<br>
<br>

### ⑵ 라벨 정규화
data.json 안에서 같은 의미의 라벨이 여러 표기로 섞여 있습니다.

| 원본 | 위치 | 표준 라벨 |
|---|---|---|
| `+` | expected | Cross |
| `cross` | filter 키 | Cross |
| `x` | expected, filter 키 | X |

`normalize_label()`이 대소문자·공백을 정리한 뒤 위 표대로 변환합니다.
콘솔 출력과 PASS/FAIL 비교는 모두 표준 라벨 기준입니다.
정규화를 하지 않으면 `"+" != "cross"`가 되어 모든 Cross 케이스가 FAIL이 됩니다.

<br>
<br>

### ⑶ MAC 연산
- `mac(pattern, filter)` : 이중 반복문으로 같은 위치의 값을 곱해 누적합니다.
- 결과 점수가 클수록 패턴이 해당 필터와 비슷하다는 뜻입니다.
- NumPy 등 외부 라이브러리를 쓰지 않습니다.

<br>
<br>

### ⑷ 동점 처리 정책 (epsilon)
- `abs(score_a - score_b) < 1e-9` 이면 동점으로 간주합니다.
- 모드 1에서는 `판정 불가`, 모드 2에서는 `UNDECIDED`로 출력합니다.
- UNDECIDED는 expected(Cross/X)와 다르므로 FAIL로 처리합니다.

<br>
<br>

### ⑸ 모드 2 검증 (프로그램이 중단되지 않도록 케이스 단위 FAIL 처리)
- 키가 `size_N_idx` 형식이 아님 → 스키마 오류
- 해당 크기의 필터가 없음 → 스키마 오류
- input/expected 누락, 알 수 없는 라벨 → 스키마/라벨 오류
- 패턴 크기가 N×N이 아님 → 크기 불일치

<br>
<br>

### ⑹ 보너스
- **패턴 생성기**: `generate_cross(n)`, `generate_x(n)`. 성능 분석 입력으로 재활용합니다.
- **1차원 최적화**: `flatten()` + `mac_1d()`. 성능 표에 2차원과 나란히 비교합니다.

### ⑵ 실패 원인 분석

실패 원인을 **데이터/스키마 문제 · 로직 문제 · 수치 비교 문제** 세 가지로 나누어 진단했습니다.

① **데이터/스키마 문제 (라벨)**: expected는 `+`, 필터 키는 `cross`로 표기가 달랐습니다.
   정규화를 적용해 Cross 케이스(size_5_2, size_25_2)를 올바르게 PASS시켰으므로, 남은 FAIL은 라벨 문제가 아닙니다.

<br>

② **로직 문제**: MAC 연산을 손으로 검산한 결과와 프로그램 점수가 일치했습니다.
   또한 크기 선택(size_N → 필터)이 정상 동작했으므로 로직 문제도 아닙니다.

<br>

③ **수치 비교 문제 + 필터 데이터 설계 (실제 원인)**: 실패한 3개는 모두 두 필터 점수가 **수학적으로 같은** 경우입니다.
   - size_5_1: X 필터 값이 0.1로 작고, Cross 필터 가운데가 0.9입니다. X 패턴(1이 9개) × 0.1 = 0.9, Cross 필터와는 가운데 한 칸만 겹쳐 0.9 → 동점.
   - size_13_2: X 필터 가운데가 7.5라서, + 패턴과 X 필터가 가운데 한 칸만 겹쳐도 7.5입니다. Cross 필터는 0.3 × 25칸 = 7.5 → 동점.
   - size_25_1: Cross 필터 가운데가 4.9, X 필터는 0.1 × 49칸 = 4.9 → 동점.

<br>

④ 부동소수점 덧셈은 순서에 따라 `0.9` vs `0.8999999999999999`처럼 미세한 차이가 생깁니다.
   epsilon 없이 `>`로 비교했다면 size_5_1은 "Cross 승"(0.9 > 0.8999…)으로 판정되었을 것입니다.
   이는 수학적으로 근거 없는 판정이므로, epsilon 비교로 동점(UNDECIDED)을 정확히 잡아낸 것이 올바른 동작입니다.

<br>

⑤ 결론: FAIL 3건은 **프로그램 오류가 아니라 필터 가중치가 두 클래스를 구별하지 못하도록 구성된 데이터 문제**입니다.
   개선하려면 필터 값을 고르게(예: 모양 위치 1.0, 나머지 0) 맞추거나, 점수를 필터 가중치 합으로 나누는 정규화가 필요합니다.
   다만 과제 요구사항(UNDECIDED는 FAIL)을 지키기 위해 데이터와 정책은 그대로 두고 원인만 보고합니다.

<br>

### ⑶ 성능 분석 (10회 평균, 측정 환경에 따라 값은 달라짐)

| 크기 | 2차원 평균(ms) | 1차원 평균(ms) | 연산 횟수(N²) |
|---|---|---|---|
| 3×3 | 0.000693 | 0.000587 | 9 |
| 5×5 | 0.001302 | 0.000804 | 25 |
| 13×13 | 0.005962 | 0.004255 | 169 |
| 25×25 | 0.022023 | 0.020213 | 625 |

<br>
<br>

### ⑷ 시간 복잡도 분석 — O(N²)

1. MAC 연산은 N×N의 모든 칸에 대해 곱셈 1번, 덧셈 1번을 합니다. 따라서 연산 횟수는 정확히 **N²**입니다.
2. 반복문이 행 N번 × 열 N번으로 중첩되어 있으므로 시간 복잡도는 **O(N²)**입니다.
3. 측정 결과도 이를 뒷받침합니다. 5×5 → 25×25는 N이 5배, N²가 25배(25 → 625) 증가했습니다.
   측정 시간은 약 0.0013ms → 0.022ms로 **약 17배** 증가했습니다.
4. 13×13 → 25×25도 N²는 약 3.7배(169 → 625), 시간은 약 3.7배(0.0060 → 0.0220)로 거의 비례합니다.
5. 작은 크기(3×3, 5×5)에서는 함수 호출·반복문 준비 같은 **고정 비용**이 상대적으로 커서 비례 관계가 약간 덜 맞습니다.
   크기가 커질수록 N²에 가까워집니다.
6. 1차원 버전은 인덱스 계산(`pattern[i][j]` → `pattern[k]`)이 한 단계 줄어들어 조금 더 빠릅니다.
   하지만 연산 횟수는 똑같이 N²이므로 시간 복잡도는 변하지 않습니다(상수 배 개선).
7. 시간 측정은 `time.perf_counter()`로 **연산 함수 호출 구간만** 측정했습니다. 입력·출력·파일 읽기는 제외했습니다.
8. 1회 측정은 너무 짧아 오차가 크므로 10회 반복 후 평균을 냈습니다.

<br>
<br>

### ⑸ 대형 N(1000×1000) 처리 시 시간·메모리 분석

#### ① 실측 결과 (본 프로그램의 `mac`, `mac_1d` 그대로 사용)

| 크기 | 연산 횟수(N²) | 2차원 평균(ms) | 1차원 평균(ms) | 1회 연산당 시간 |
|---|---|---|---|---|
| 25×25 | 625 | 0.033 | 0.035 | 약 53 ns |
| 100×100 | 10,000 | 0.535 | 0.561 | 약 53 ns |
| 500×500 | 250,000 | 9.463 | 7.588 | 약 38 ns |
| 1000×1000 | 1,000,000 | 38.389 | 30.606 | 약 38 ns |

※ 측정 환경에 따라 절대값은 달라질 수 있지만, N²에 비례하는 경향은 같습니다.

<br>
<br>

#### ② 시간 추정
- 1000×1000은 MAC 1회에 곱셈·덧셈이 각 100만 번입니다. 실측 약 **38ms**입니다.
- 패턴 1개 판정에는 필터 2개(Cross, X)가 필요하므로 약 **77ms**가 걸립니다.
  패턴 1,000개를 판정하면 약 **77초**입니다.
- N이 2배(2000×2000)가 되면 O(N²)에 따라 시간은 약 4배(약 150ms/회)로 늘어납니다.
- 만약 큰 이미지 위에서 k×k 필터를 밀면서 계산하는 **합성곱(convolution)** 형태라면 연산량은 O(N²·k²)이 됩니다.
  예를 들어 1000×1000 이미지에 25×25 필터를 쓰면 약 6.25억 번입니다.
  연산당 38ns로 계산하면 순수 Python으로 약 24초가 걸리므로 최적화가 필수입니다.

<br>
<br>

#### ③ 메모리 추정
- Python 리스트는 숫자를 바로 저장하지 않고, **float 객체(24바이트)를 가리키는 포인터(8바이트)**를 저장합니다.
- 서로 다른 값으로 채운 1000×1000 행렬 1개를 실측하면 약 **33MB**입니다(원소당 약 32바이트).
  같은 크기를 C의 `double` 배열로 저장하면 8MB이므로, 약 4배 더 씁니다.
- 판정에는 패턴 1개와 필터 2개가 필요하므로 약 **100MB**입니다.
  1차원 변환 복사본까지 만들면 일시적으로 약 2배까지 늘어납니다.
- 행마다 따로 할당된 리스트라서 메모리에 흩어져 있고, 원소마다 포인터를 한 번 더 따라가야 합니다(간접 참조).
  그래서 CPU 캐시 효율이 낮아집니다.

<br>
<br>

#### ④ 우선 적용할 최적화 (효과가 큰 순서)
1. **메모리 접근 최적화 (1순위)**: 2차원 → 1차원 연속 배열로 바꿉니다(본 과제의 보너스 구현).
   실측에서 1000×1000 기준 약 20% 빨라졌습니다(38.4 → 30.6ms).
   표준 라이브러리 `array('d')`를 쓰면 포인터 없이 8바이트 double을 연속으로 저장하므로 메모리가 약 1/4로 줄어듭니다.
2. **스트라이드(접근 순서) 최적화**: 항상 행 우선(`i` 바깥, `j` 안쪽)으로 접근해 메모리를 순서대로 읽습니다.
   열 우선으로 읽으면 매번 다른 행 리스트로 건너뛰어 캐시 미스가 늘어납니다.
3. **블록(타일) 연산**: 행렬을 예: 64×64 블록으로 나눠, 한 블록이 CPU 캐시(L1/L2)에 들어간 상태에서 계산을 끝냅니다.
   특히 합성곱처럼 같은 데이터를 여러 번 재사용하는 경우에 효과가 큽니다.
   또한 블록 단위로 나누면 다음 단계인 병렬화의 작업 단위로 그대로 쓸 수 있습니다.
4. **병렬화**: 블록별 부분합을 여러 코어에서 계산한 뒤 마지막에 한 번만 더합니다.
   단, Python은 GIL 때문에 `threading`으로는 계산이 빨라지지 않습니다.
   `multiprocessing`(표준 라이브러리)을 써야 하는데, 프로세스 간 데이터 복사 비용이 있습니다.
   그래서 연산량이 작은 경우(본 과제의 25×25 이하)는 오히려 느려지고, 큰 N이나 패턴 여러 개를 나눠 처리할 때만 이득입니다.
5. **조기 종료/희소성 활용**: 본 데이터처럼 0이 대부분인 필터는 0이 아닌 위치만 저장해 계산하면 연산 횟수가 N²에서 실제 값 개수로 줄어듭니다.
   예: 1000×1000 X 필터는 약 2,000칸만 0이 아니므로 약 500배 감소합니다.

### ⑹ CPU(직렬) vs NPU/GPU(병렬) 관점의 병목

#### ① 왜 MAC이 AI에서 중요한가
- 신경망의 합성곱층·완전연결층 계산은 거의 전부 MAC의 반복입니다.
- 그래서 AI 하드웨어 성능은 "초당 MAC 연산 수(TOPS)"로 표시됩니다.

<br>
<br>

#### ② CPU의 병목 — 직렬 처리
- 본 프로그램은 `total += a * b`를 **한 번에 하나씩 순서대로** 계산합니다.
  `total`이 이전 결과에 의존하므로 다음 연산이 앞의 연산을 기다려야 합니다(데이터 의존성).
- CPU 코어 수는 보통 수 개~수십 개라서 병렬화해도 한계가 있습니다.
- 순수 Python은 연산 1회마다 객체 생성·타입 확인이 들어가 연산당 약 38ns가 걸립니다.
  같은 계산을 C로 하면 1ns 이하이므로, 계산보다 **인터프리터 오버헤드**가 병목입니다.

<br>
<br>

#### ③ NPU/GPU의 병목 — 병렬 처리에서 새로 생기는 문제
NPU는 수천 개의 MAC 유닛을 배열(시스톨릭 어레이 등)로 두고 동시에 계산합니다.
계산 자체는 빨라지지만, 병목이 다른 곳으로 옮겨갑니다.

| 병목 | 설명 | 사례 | 실무 대책 |
|---|---|---|---|
| **메모리 대역폭** | MAC 유닛은 빠른데 데이터를 메모리에서 가져오는 속도가 못 따라감 | 1000×1000 MAC은 데이터 8MB×2를 읽고 연산은 100만 번뿐. 연산 대비 읽는 양이 많아 유닛이 대부분 놀게 됨 | 블록화로 데이터를 칩 내부 SRAM에 올려 재사용, 8bit 정수(INT8) 양자화로 읽을 양을 1/4로 축소 |
| **데이터 전송** | CPU 메모리 → NPU/GPU 메모리로 복사하는 비용 | 25×25처럼 작은 연산은 복사 시간이 계산 시간보다 큼 | 여러 패턴을 묶어 한 번에 보내기(배치 처리), 데이터를 장치에 계속 둔 채 재사용 |
| **동기화 비용** | 병렬로 계산한 부분합을 하나로 더할 때 서로 기다림 | 1,000개 유닛이 각각 계산한 부분합을 `total`에 합치는 단계 | 트리 형태 합산(reduction)으로 기다림을 log 단계로 축소, 동기화 횟수 최소화 |
| **병렬화 한계(암달의 법칙)** | 병렬화 안 되는 부분(파일 읽기, 판정, 출력)이 전체 속도를 제한 | 본 프로그램의 JSON 로드·라벨 정규화·출력은 직렬 | 계산 외 단계를 최소화하고 I/O와 계산을 겹쳐서 실행 |
| **작은 문제의 비효율** | 유닛 수보다 연산이 적으면 대부분의 유닛이 놂 | 3×3(9번 연산)을 수천 유닛 NPU에서 돌리면 활용률 1% 미만 | 작은 연산은 CPU에서 처리, 큰 연산·배치만 NPU로 보냄 |

#### ④ 정리
- **CPU**: 연산이 순서대로 실행되는 것이 병목입니다. 작은 N에 유리하고 전송 비용이 없습니다.
- **NPU/GPU**: 계산은 빠르지만 **메모리 대역폭·전송·동기화**가 병목입니다. 큰 N과 배치 처리에 유리합니다.
- 따라서 실무에서는 연산량이 적은 작업은 CPU에, 연산량이 많고 데이터를 재사용하는 작업은 NPU에 맡깁니다.
  또한 블록화·양자화·배치 처리로 "데이터를 덜 옮기고 많이 재사용하는" 방향으로 최적화합니다.
